MCU / server 对接补充 2026-10-14
适用于本次 MCU bridge 与同步更新的 wifi/server/app.py。
UART version=1、HTTP 路径和所有字节布局保持原样。

1. 命令 ID 的分配增加约束
服务器 command_id 是 32 位小写 hex；按 hex 数值严格递增。
首次从随机 128-bit 值开始，后续在 SQLite 事务中分配 high-water + 1。
高水位持久保存在 service_meta，兼容旧数据库的 MAX(commands.id)，不依赖电脑时钟。
request_id、event_id、lease_id 和 photo_id 不适用此排序规则。
这是服务器负责的 ID 分配行为；ESP 继续 unhex 后原样转发 16 字节，
不用计算 ID、不用改变协议编码，也不需要自动重放旧命令。

MCU 在一次启动期间保存最近 8 个命令结果和最大已接受 command_id。
重复且仍在缓存：返回原 ACK/RESULT；同 ID 不同参数：CONFLICT。
缓存已淘汰、ID <= high-water：COMMAND_ACK=UNKNOWN_ID，RESULT=unknown；绝不再执行。
新 ID 大于 high-water：按正常忙/参数检查接受。没有运行 8/16 次后必须重启的限制。
HELLO 或 ESP 新 session 不清除业务高水位。MCU 重启后仍无持久命令账本，
继续执行 INTERFACE_REVIEW 中的 unknown 禁止自动重放规则。
联调模拟端请按递增 ID 发新命令；不要用随机且可能倒退的 ID 充当新动作。
必须使用本次更新后的 server；旧随机 ID 版本 server 不适合配合本次 MCU。

2. MCU 实现边界
- 所有已定义请求 payload <=24；MCU 对超过 64 字节的编码请求直接丢弃至 00。
  正常请求完全符合 v1；回复仍支持完整 544 字节 payload / 512 字节照片块。
- BUSY 响应会被传输层缓存；等待后应使用新 seq 查询。当前 Arduino 实现符合。
- PHOTO_NEXT 不再同步挂载/扫描：首次 BUSY，主循环分批准备，随后新 seq 获取结果。
  CRC 在保存阶段增量生成，不在 NEXT 重扫全图；详见 PHOTO_NEXT_LATENCY_REVIEW.txt。
- TIME_RESULT 在硬件写后回读完成后返回 verified=1；3.5s 未完成返回 IN_PROGRESS/verified=0，不能当作未写入。
- USB/触屏/UI 与 UART 共用现有菜单提交入口；USART1 仍处理 PC RTC 命令。

3. 照片持久化
- 新完成的 Txxxxxxx.BMP 配套 Txxxxxxx.WFM（带 CRC 元数据、ID、长度、整图 CRC、时间）。
- 只有完整关闭并写好元数据的照片才供 PHOTO_NEXT 读取；旧 BMP 不自动导入。
- PHOTO_COMMIT 写追加确认记录，重复提交幂等，不删除 BMP。
- 元数据仍完整但确认记录写断电：下次重传/确认；元数据损坏则跳过，不冒充已上传。
- 拔卡/换卡导致句柄失效时重新挂载；旧 ID 不能用于新卡上的其他照片。
- FAT 本身不提供事务性掉电保障；这里的 CRC/提交记录不等于整个 SD 文件系统防掉电。
