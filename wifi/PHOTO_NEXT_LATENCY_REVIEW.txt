PHOTO_NEXT 时延审查与修改 / 2026-10-14

已确认原实现不会在 PHOTO_NEXT 重算整图 CRC。BMP 保存时，put() 对每次成功写入的
最多 768 字节增量计算 CRC32；文件完整关闭后，WFM 保存最终 CRC/长度/稳定 ID。
NEXT 仅读取这份 40 字节元数据，不重新扫描 691254 字节图片。

发现并修正的阻塞点：
- 原 NEXT 在 UART dispatch 内直接挂载/扫描文件系统；卡初始化允许等待约 2 秒，
  多次扇区读取也会累积延迟。wifi_polling 防重入期间无法及时答复 ESP 重试。
- 现在 NEXT 本身不执行任何存储 I/O：首次返回 BUSY，主循环 recorder_poll 准备。
- 每轮最多扫描 8 个目录项；未找到时自动下一轮继续，不等待下一次 ESP 请求。
- SD 等待仍通过 service_hook 处理 UART：HELLO 可响应，NEXT 准备中返回 BUSY。
- READ/COMMIT 在 SD 服务回调中立即返回 BUSY，不重入 FatFs、不挂起请求等拍照结束。
- CRC/关闭文件条件/稳定 photo_id/COMMIT 不删除 BMP 等协议要求不变。

ESP 配合：
- 1 秒普通 RPC 超时和同 seq 丢包重试保持原方案即可。
- BUSY 是已收到的有效回复，会被传输层缓存；稍后查询必须使用新 seq。
  相同 seq 重试仍重放原 BUSY，这是幂等缓存行为。现有 app.cpp 已按此处理。
- 已准备的照片仅在 ESP 下一次请求时响应，不会在 HTTPS 上传期间主动推流。

验证：
- 实际 FatFs + SDHC 模型断言：每次 NEXT 调用的 SD 读命令数保持不变；准备期间
  service_hook 再次调用 NEXT 得到 BUSY；长目录分多轮后台推进，读取量只包含元数据。
- 完整 BMP CRC、重启 ID、重复 COMMIT、写断提交记录、原图保留及录制错误回归通过。
- Test-WifiBridge.ps1 回归通过；最终后台连续扫描调整另重跑 SD 测试通过。
- ESP 实际主机状态机 + MCU transport adapter + server TestClient 联测重跑通过：
  25 HTTP 请求、事件/块回包丢失恢复、一次拍照、一次 COMMIT、可下载有效 BMP。
  此联测的存储端是模型，不能代替板端 SD 最大延迟测量。
- 实际 READ/COMMIT 的同步 SD I/O 在异常卡上仍可能超过 1 秒，尚无实机最坏时延保证。
