RTC 异步回复与命令账本复核 / 2026-10-14

结论基于本次现场源码，供 ESP 对话同步；协议和行为无需修订。

1. TIME_RESULT 缓冲区
当前 FDwork/shared/wifi_transport.h 的 wifi_reply() 使用 uint8_t *p=t->reply，
在 reply 中补头、计算 CRC、原地 COBS 编码；rx 只保存输入帧。
wifi_dispatch() 的输出参数同样是 t->reply+14。
因此 wifi_pending_poll() 写 wifi_link.reply[14]/[15] 正确，不能改为 rx。
此前“输出与接收帧别名”的旧注释已修正，避免误导；没有修改运行行为。

本次新增 tests/test_wifi_uart.c 完整路径测试：
- 编码 TIME_SET → 有限 RX FIFO → 实际 USART0 IRQ → wifi_mcu_poll/dispatch。
- 验证 FPGA 校时触发字、异步所有权和启动时记录的硬件完成序号。
- 旧序号完成标志、busy 未解除均不提前回复。
- 模拟硬件成功 / 校验失败 / 3.5s 超时 / MCU 毫秒计数回绕。
- 故意使 rx[14]/[15] 与结果不同，验证输出确实来自 reply。
- 实际 TX IRQ 排出整帧，再校验 COBS、CRC、类型、session、seq、状态和 verified。
- 相同 seq/body 重试返回原结果，硬件状态变化也不会再次写 RTC。
TIME_RESULT 超时仍为 IN_PROGRESS/verified=0，表示结果未知，不表示未写入。

2. 持续命令操作
当前 WIFI_HISTORY=8，是可淘汰终结结果的缓存，并非永不淘汰的 16 条账本。
最大已接受 command_id 单独保存为 16 字节 high-water。
有空位则使用空位，否则淘汰 ID 最小的已终结项；待完成项不会被淘汰。
只有全为待完成项时，容量本身才会造成 BUSY；录制资源忙也可能造成 BUSY。
这不是每次启动 8/16 次动作的终身额度。任务完成后缓存可继续循环使用。

本次 test_wifi_mcu.c 在已有 65 次命令测试后，继续执行 1024 次新动作而不复位；
重复最后 ID 不重复执行，淘汰旧 ID 返回 UNKNOWN_ID；随后通过真实 dispatch
填满 8 条待完成 STOP，验证第 9 条 BUSY 且不前移 high-water，录制安全边界
完成后相同业务 ID 可被接受，最旧已淘汰 ID 仍不能重放。

持续使用约束必须同时满足：
- server SQLite 持久分配严格递增的 128-bit command_id，ESP 原样传递。
- 已淘汰结果不能还原，返回 UNKNOWN_ID/unknown；不能将其当 BUSY 反复重试动作。
- MCU 重启丢失 RAM 账本，不承诺跨断电 exactly-once；结果未知禁止自动重放。
- 若底层任务始终不完成，BUSY 可能持续；不能仅按时间淘汰待完成项来重执行。
- 传输 seq 与业务 command_id 不同；BUSY 缓存后续重试用新 seq。
详见 MCU_PROTOCOL_ADDENDUM.txt，旧随机命令 ID 服务端不兼容此约束。

3. PHOTO_COMMIT 协作
同意 ESP 收到 BUSY 后保留服务器已验证完整的状态，稍后用新 seq 重试 COMMIT，
不重传图片、不删除照片。重复 COMMIT 在 MCU 侧幂等，匹配 ID/size/CRC 后写确认记录。
本次没有修改 wifi/esp8266/；其状态机修改和目标编译由 ESP 对话负责。
