Observed on the board (user log 22:34:04):

  RTC trusted=1; SD init completed.
  MCAUSE=0x38000007 MDCAUSE=2 MEPC=0x08000B7C MTVAL=0x11010010.

Decoded against RAM ELF SHA256
  ce468544865cda5a51551543dabdb739c317804a9cc0d43927bc592aea0c6291:
  wifi_mcu_init, called by main after recorder_init and before the UI loop.
  0x08000B76 stores zero to USART0 interrupt configuration at 0x11010010.
  MEPC is several instructions later; do not treat that arithmetic instruction
  as the offending memory access. The fault address identifies USART0, not USB.
  SDK MDCAUSE=2 denotes instruction access error rather than PMP subcause=1.
  The low exception cause is store access fault.

What is confirmed:
  USB enumeration succeeded. The MCU traps during Wi-Fi startup, before touch
  polling. USART0 base 0x11010000 and MISC clock/reset bit 1 match the SDK.
  The original BSP board_init only initializes USART1. Wi-Fi initializes UART0
  itself, previously without any delay/barrier between clock, reset and MMIO.
  This is independent of ESP UART traffic: it fails before RX is enabled.

Candidate correction (not yet verified on hardware):
  Mask the USART0 ECLIC IRQ while resetting/configuring it.
  Enable USART0 clock, fence + 50-us SDK delay; assert reset, fence + delay;
  release reset, fence + delay; then access the USART0 registers.
  Print MISC clock/reset/divider immediately before the first UART access.
  Keep UART0 enabled, protocol unchanged, IRQ registration and USB path intact.
  No FPGA, pin assignment, JTAG or reset-vector changes in this correction.
  The current evidence does not prove reset synchronization is the sole cause.

Validation:

  UART MMIO while gated/reset/unsettled. Old code fails this model; new code
  passes. This model checks ordering, not the physical PH1P implementation.
  tests/Test-WifiBridge.ps1 passed (UART, protocol, menu, RTC, SD and formatter).
  Log: build/wifi_uart_reset_tests.log.
